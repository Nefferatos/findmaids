# Creating an admin account in Supabase

How to bootstrap an `ADMIN` in a Supabase project (staging ref `tajpujqabclbxoggkxse`, or the production project). Read the access rules in [ADMIN_GUIDE.md](ADMIN_GUIDE.md) and the project variables in [STAGING.md](STAGING.md) first.

## Rules that constrain this procedure

- Never add a default admin password and never promote an unverified or disabled account. The bootstrap is a deliberate, logged, one-account-at-a-time action.
- `auth.ts` `authorize()` returns `null` unless the password is accepted by Supabase Auth (or, for an account that predates the integration, by its bcrypt `passwordHash`) **and** the row has `emailVerified` and `disabled = false`. A row without those cannot sign in, however the role is set.
- The SQL/script bootstrap below writes a bcrypt `passwordHash` only. That still works: the first successful sign-in creates the Supabase identity with the same password and stores `User.supabaseUserId`, after which Supabase owns the credential (see [SUPABASE_SETUP.md](SUPABASE_SETUP.md)).
- An `ADMIN` is redirected to `/admin/2fa` until TOTP is enrolled and the session is MFA-verified (`lib/security/admin-mfa.ts`, `lib/admin-auth.ts`). Password-only admin access is not possible by design, so expect the first sign-in to stop at the 2FA screen.
- Every bootstrap writes an `AuditLog` row. Record who created which account and why.
- `SUPABASE_SERVICE_ROLE_KEY` is server-only and bypasses RLS. Never put it in a browser bundle, a `NEXT_PUBLIC_*` variable, a log line or a chat message.

## Before you start: which schema does the app read?

The app resolves its schema from `DATABASE_SCHEMA` and defaults to **`findmaids`** (`lib/prisma.ts`, `lib/prisma-script.ts`).

| Where the tables are                                                                      | What the app needs                                                     |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `public` (the result of `supabase/staging-setup.sql` pasted into the Supabase SQL editor) | `DATABASE_SCHEMA=public`, or `?schema=public` on the connection string |
| `findmaids` (a dedicated schema you created with `CREATE SCHEMA findmaids`)               | the default; no extra setting                                          |

Confirm what the Supabase project actually has:

```sql
select table_schema, count(*)
from information_schema.tables
where table_name in ('User', 'Agency', 'Plan')
group by table_schema;
```

All commands below use `public."User"`. Replace `public` with `findmaids` if that is your layout.

## Required columns for a working admin

| Column              | Value                                          | Why                                                        |
| ------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| `id`                | any unique `TEXT`; the SQL below generates one | `@default(cuid())` is generated by Prisma, not by Postgres |
| `email`             | lower-case, unique                             | login identity; `authorize()` lower-cases input            |
| `role`              | `'ADMIN'`                                      | `"UserRole"` enum                                          |
| `passwordHash`      | bcrypt cost 10 hash                            | legacy login; linked to Supabase Auth on first sign-in       |
| `emailVerified`     | `now()`                                        | required for credentials login                             |
| `passwordChangedAt` | `now()`                                        | invalidates any JWT issued before the password was set     |
| `disabled`          | `false`                                        | `true` blocks login and every protected request            |
| `totpEnabled`       | `false` to start                               | must become `true` through `/admin/2fa` enrolment          |
| `updatedAt`         | `now()`                                        | `NOT NULL` with no database default                        |

## Method A — Supabase SQL editor (recommended)

No long-lived secret leaves your machine and the whole change is one transaction.

1. Generate the hash locally (the repo already has `bcryptjs`):

```powershell
cd c:\findmaids-main
$hash = node -e "console.log(require('bcryptjs').hashSync('PASTE-A-LONG-RANDOM-PASSWORD',10))"
$hash
```

Keep the single quotes: a bcrypt hash contains `$2b$10$…`, and PowerShell would interpolate `$2b` etc. inside double quotes.

2. Supabase dashboard → **SQL Editor** → new query → paste this, replacing the email, name and hash:

```sql
with new_admin as (
  insert into public."User" (
    id, email, name, role, "passwordHash", "emailVerified",
    "passwordChangedAt", disabled, "totpEnabled", "createdAt", "updatedAt"
  )
  values (
    'c' || substr(md5(random()::text || clock_timestamp()::text), 1, 24),
    lower('admin@yourdomain.com'),
    'FindMaids Admin',
    'ADMIN',
    '<PASTE_BCRYPT_HASH>',
    now(),
    now(),
    false,
    false,
    now(),
    now()
  )
  on conflict (email) do update
    set role = 'ADMIN',
        "passwordHash" = excluded."passwordHash",
        "emailVerified" = excluded."emailVerified",
        "passwordChangedAt" = excluded."passwordChangedAt",
        disabled = false,
        "updatedAt" = now()
  returning id, email, role
)
insert into public."AuditLog" (
  id, "userId", action, entity, "entityId", metadata, "createdAt", "updatedAt"
)
select
  'c' || substr(md5(random()::text || clock_timestamp()::text), 1, 24),
  id, 'BOOTSTRAP_ADMIN_CREATION', 'User', id,
  jsonb_build_object('method', 'sql_editor', 'mfaEnrolmentRequired', true),
  now(), now()
from new_admin;
```

3. Verify (expect `role = ADMIN`, `verified = true`, `disabled = false`, `totp = false`):

```sql
select id, email, role,
       "emailVerified" is not null as verified,
       disabled, "totpEnabled"
from public."User"
where email = lower('admin@yourdomain.com');
```

The SQL editor connects as the table owner, which bypasses the RLS policies (`20261103000000_enable_rls`). That is why this works here while the anon/authenticated API cannot read the table at all.

## Method B — service-role REST call (automation, `public` schema only)

Use this when the account must be created by a script or from a machine where the Supabase dashboard is awkward. It uses PostgREST with the server-only service-role key, which bypasses the RLS policies.

**Limitation:** the project's API exposes only `public` and `graphql_public`; any other schema answers `PGRST106 Invalid schema`. If your tables live in `findmaids`, expose that schema in Supabase → Project Settings → API → Exposed schemas, or use Method A or C.

Save as `create-admin.mjs` in the repo root, run it once, then delete it:

```js
// node create-admin.mjs   (Node 20+; bcryptjs comes from the repo's node_modules)
import { readFileSync } from "node:fs";
import { randomBytes, randomInt } from "node:crypto";
import { hashSync } from "bcryptjs";

const env = Object.fromEntries(
  readFileSync(".env", "utf8")
    .split(/\r?\n/)
    .map((line) => /^\s*([A-Za-z_][A-Za-z0-9_]*)\s*=(.*)$/.exec(line))
    .filter(Boolean)
    .map((m) => [
      m[1],
      m[2].trim().replace(/^(".*"|'.*')$/, (v) => v.slice(1, -1)),
    ]),
);

const EMAIL = (process.env.ADMIN_EMAIL || "admin@yourdomain.com").toLowerCase();
const NAME = process.env.ADMIN_NAME || "FindMaids Admin";
const alphabet = "ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz23456789";
const PASSWORD =
  process.env.ADMIN_PASSWORD ||
  Array.from({ length: 20 }, () => alphabet[randomInt(alphabet.length)]).join(
    "",
  );

const now = new Date().toISOString();
const key = env.SUPABASE_SERVICE_ROLE_KEY;
const url = env.SUPABASE_URL.replace(/\/+$/, "");
const headers = {
  apikey: key,
  Authorization: `Bearer ${key}`,
  "Content-Type": "application/json",
  Prefer: "resolution=merge-duplicates,return=representation",
};

const res = await fetch(`${url}/rest/v1/User?on_conflict=email`, {
  method: "POST",
  headers,
  body: JSON.stringify([
    {
      id: "c" + Date.now().toString(36) + randomBytes(6).toString("hex"),
      email: EMAIL,
      name: NAME,
      role: "ADMIN",
      passwordHash: hashSync(PASSWORD, 10),
      emailVerified: now,
      passwordChangedAt: now,
      disabled: false,
      totpEnabled: false,
      createdAt: now,
      updatedAt: now,
    },
  ]),
});
if (!res.ok) {
  console.error(
    `Supabase refused the insert: ${res.status} ${await res.text()}`,
  );
  process.exit(1);
}
const [user] = await res.json();
console.log(`created ${user.email} (${user.role}) id=${user.id}`);

await fetch(`${url}/rest/v1/AuditLog`, {
  method: "POST",
  headers,
  body: JSON.stringify([
    {
      id: "c" + Date.now().toString(36) + randomBytes(6).toString("hex"),
      userId: user.id,
      action: "BOOTSTRAP_ADMIN_CREATION",
      entity: "User",
      entityId: user.id,
      metadata: {
        method: "service_role_postgrest",
        mfaEnrolmentRequired: true,
      },
      createdAt: now,
      updatedAt: now,
    },
  ]),
});

console.log(`email:    ${EMAIL}`);
console.log(`password: ${PASSWORD}`);
```

```powershell
$env:ADMIN_EMAIL = "admin@yourdomain.com"
node create-admin.mjs
Remove-Item create-admin.mjs
```

`Prefer: resolution=merge-duplicates` together with `on_conflict=email` makes the call idempotent: re-running it re-hashes the password and re-asserts `role = ADMIN` instead of failing on the unique index.

## Method C — promote an account that already exists

Preferred for a real person: they register through `/register`, verify their email, then you promote the existing row. This is the only path that does not invent credentials.

```powershell
cd c:\findmaids-main
Copy-Item .env .env.deploybak      # .env.deploybak is git-ignored
# edit .env: DATABASE_URL (transaction pooler, 6543), DIRECT_URL (session pooler, 5432),
#            DATABASE_SCHEMA=public, APP_ENV=staging, STAGING_PROJECT_REF=<project-ref>
$env:ADMIN_EMAIL = "person@yourdomain.com"
$env:CONFIRM_ADMIN_PROMOTION = "person@yourdomain.com"
npm run admin:promote
Move-Item .env.deploybak .env -Force
```

- `scripts/promote-admin.ts` refuses accounts that are missing, unverified or disabled, and writes `BOOTSTRAP_ADMIN_PROMOTION` to `AuditLog`.
- The scripts reload `.env` themselves (`lib/prisma-script.ts` → `loadEnvFile`), and the file **overrides** inherited shell variables. Exporting `DATABASE_URL` in the terminal will not retarget the script, so edit the file.
- Google-only accounts have no `passwordHash`; set one with Method A's `UPDATE`, or have the user use the password-reset flow first.

## First sign-in and TOTP

1. Open `/login` and sign in with the email and password.
2. You are redirected to `/admin/2fa`. Choose **Set up authenticator**, scan the QR code, enter the current six-digit code and confirm.
3. TOTP parameters are otplib defaults: SHA-1, 6 digits, 30-second period, issuer `FindMaids Admin`, so any standard authenticator app works.
4. After enrolment every sign-in needs the code, and Google sign-in is refused for TOTP-enabled admins.
5. `/admin` then loads normally.

`TOTP_ENCRYPTION_KEY` must be identical in every environment that signs in. The secret is stored with AES-256-GCM under that key (`lib/totp.ts`), so if the Cloudflare Worker uses a different value than the environment where you enrolled, `decryptTotpSecret()` throws and the admin cannot sign in at all. Generate a key with:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

and set the same value in `.env` and with `npx wrangler secret put TOTP_ENCRYPTION_KEY`.

## Local testing without an authenticator app

ADMIN accounts normally need TOTP before any admin page or admin API responds.
Two options make that testable without a phone.

**1. Development-only MFA bypass (fastest).** Add to the ignored `.env`:

```dotenv
ADMIN_MFA_BYPASS="true"
```

Restart the dev server. Any ADMIN account (enrolment not required) can then reach
the admin pages and APIs. The flag is ignored when `NODE_ENV=production`, and
`lib/security/env-guard.ts` refuses to start a production build if it is set, so
it cannot reach a deployment. Everything else still applies: role checks, audit
logos, same-origin CSRF and rate limits.

**2. Real TOTP flow without a phone.** Enrol once at `/admin/2fa`, then print the
current code from the terminal:

```powershell
npm run admin:totp -- admin@findmaids.test
```

It decrypts `totpSecret` with `TOTP_ENCRYPTION_KEY`, prints the 6-digit code (and
the `otpauth://` URI) and verifies the code before printing it. The script uses
`DATABASE_URL`/`DIRECT_URL` from `.env`, so point those at the database being
tested first. `TOTP_ENCRYPTION_KEY` must be a base64-encoded 32-byte key:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Rotating that key makes existing enrolments unreadable; reset 2FA for the account
and enrol again.

## Rotating, disabling and removing

| Goal                | Statement                                                                                                                                    | Notes                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Rotate the password | `update public."User" set "passwordHash" = '<new hash>', "passwordChangedAt" = now(), "updatedAt" = now() where email = '<email>';`          | `passwordChangedAt` after a token's `iat` invalidates existing sessions (`auth.ts` jwt callback) |
| Suspend access      | `update public."User" set disabled = true, "updatedAt" = now() where email = '<email>';`                                                     | Checked on every JWT refresh and protected request                                               |
| Reset 2FA           | `update public."User" set "totpEnabled" = false, "totpSecret" = null, "totpVerifiedAt" = null, "updatedAt" = now() where email = '<email>';` | Only when the key was lost or changed; re-enrol afterwards                                       |
| Demote to staff     | `update public."User" set role = 'STAFF', "updatedAt" = now() where email = '<email>';`                                                      | STAFF cannot view payments, plans, roles or settings                                             |
| Delete              | `delete from public."User" where email = '<email>';`                                                                                         | Prefer disabling: agencies, audit rows and payments reference the user                           |

Append an `AuditLog` row for each of these, as `promote-admin.ts` does.

## Verification checklist

- [ ] `select email, role, "emailVerified" is not null, disabled, "totpEnabled" from public."User" where email = '<email>';` shows `ADMIN`, `true`, `false`, `false`
- [ ] The hash matches the password you are handing over: `node -e "console.log(require('bcryptjs').compareSync('THE-PASSWORD','THE-HASH'))"` prints `true`
- [ ] `/login` succeeds and lands on `/admin/2fa`
- [ ] TOTP enrolment completes and `/admin` loads
- [ ] `AuditLog` contains the bootstrap row
- [ ] The account exists, with the same hash, in every environment the person will use (local, staging, production) — or you have told them which one to use
- [ ] The password was delivered out of band and stored in a password manager

## Troubleshooting

| Symptom                                                           | Cause                                                                                        | Fix                                                                       |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Sign-in silently returns to `/login`                              | `emailVerified` is null, `passwordHash` is null, or `disabled` is true                       | Set the missing columns (Method A)                                        |
| Login works, every admin page bounces to `/admin/2fa`             | `totpEnabled` is false, or the session is not MFA-verified                                   | Enrol TOTP, then sign in with the code                                    |
| Correct TOTP code rejected in the deployed app                    | Different `TOTP_ENCRYPTION_KEY` per environment                                              | Use one key everywhere, or reset 2FA and enrol again there                |
| `PGRST106 Invalid schema: findmaids`                              | Schema not exposed by the API                                                                | Use `public`, or add the schema in Project Settings → API                 |
| REST insert returns `401` / `PGRST301`                            | The anon or publishable key was used instead of `service_role`                               | Use `SUPABASE_SERVICE_ROLE_KEY` server-side only                          |
| `npm run admin:promote` changes the local database instead        | `.env` still holds the local URLs; the script reloads the file and overrides shell variables | Edit `.env` (keep `.env.deploybak`) and rerun                             |
| Admin pages or reports are empty although the tables have data    | App schema mismatch (`findmaids` vs `public`)                                                | Set `DATABASE_SCHEMA=public` or use `?schema=public`                      |
| `duplicate key value violates unique constraint "User_email_key"` | The email already exists                                                                     | Use the `on conflict (email) do update` form, or promote the existing row |
